# 02 导出和导入

> 原文：`zh.javascript.info/1-js/13-modules/02-import-export/article.md`
> 本篇是 `export`/`import` 的全部语法变体速查。Java 的 import 只有一种形态，JS 则有命名导出/默认导出/重导出三套玩法——其中**默认导出的坑最多**，重点看第 6、7 节。

## 知识点

### 1. 在声明前导出

`export` 放在任意声明（变量/函数/类）之前：

```js
export let months = ['Jan', 'Feb', /* ... */];
export const MODULES_BECAME_STANDARD_YEAR = 2015;
export class User {
  constructor(name) { this.name = name; }
}
```

注意：`export class`/`export function` 后**不加分号**——加了 `export` 也不会把声明变成表达式，它仍是声明，声明后面本来就不写分号。

### 2. 导出与声明分开

先声明，最后用 `export {...}` 列表统一导出（效果与逐个前置 `export` 相同）：

```js
// 📁 say.js
function sayHi(user) { alert(`Hello, ${user}!`); }
function sayBye(user) { alert(`Bye, ${user}!`); }

export {sayHi, sayBye}; // 导出变量列表（技术上也可放在函数上面）
```

### 3. `import * as <obj>`：全部导入为一个对象

```js
// 📁 main.js
import * as say from './say.js';

say.sayHi('John');
say.sayBye('John');
```

"通通导入"写着爽，但实践中**明确列出要导入的东西**更好，原因有三：

1. **tree-shaking**：打包工具（webpack 等）能检测出未使用的导出并从产物中删除，让构建更小。典型场景：项目里加了个第三方库 `say.js`，它有 `sayHi`、`sayBye`、`becomeSilent` 一堆导出函数，但你只 `import {sayHi}` ——优化器检测到这一点，会把其余未用的函数从打包产物中删掉；
2. 名字更短：`sayHi()` 而不是 `say.sayHi()`；
3. 显式导入列表让代码结构一目了然：用了什么、在哪里用，更好重构。

### 4. `import`/`export` 的 `as` 改名

```js
// 导入时改名
import {sayHi as hi, sayBye as bye} from './say.js';
hi('John');

// 导出时改名：对外的正式名称就是 hi / bye
export {sayHi as hi, sayBye as bye};
```

### 5. `export default`：默认导出

- 实践中主要有两种模块：库/函数包模块（如 `say.js`）、单实体模块（如 `user.js` 只导出一个 `class User`）。社区偏好后者——**一个模块只做一件事**，文件多不是问题，命名好 + 目录结构好反而更易导航。
- `export default` 就是为"单实体模块"准备的：

```js
// 📁 user.js
export default class User {
  constructor(name) { this.name = name; }
}

// 📁 main.js
import User from './user.js'; // 没有花括号！
new User('John');
```

- **每个文件最多一个 `export default`**。
- 新手最常见的错误就是花括号写错：

| 命名的导出 | 默认的导出 |
|---|---|
| `export class User {...}` | `export default class User {...}` |
| `import {User} from ...` | `import User from ...` |

- 技术上默认导出和命名导出可以混在一个模块里，但实践中不混用。
- 因为每文件最多一个默认导出，所以导出的实体**可以没有名字**：

```js
export default class { constructor() { ... } }        // 匿名类
export default function(user) { alert(`Hello, ${user}!`); } // 匿名函数
export default ['Jan', 'Feb', /* ... */];             // 直接导出一个值

// 对照：非默认导出必须有名字
export class { /* Error! */ }
```

#### "default" 名称

`default` 关键字可用于引用默认导出：

```js
// 函数定义与默认导出分开写（等价于函数前加 export default）
function sayHi(user) { alert(`Hello, ${user}!`); }
export {sayHi as default};

// 同时导入默认导出和命名导出（混合情况少见但存在）
import {default as User, sayHi} from './user.js';

// import * 时，默认导出就是对象的 default 属性
import * as user from './user.js';
let User = user.default;
```

#### 该不该用默认导出？（争议点）

- 命名导出**明确**：强制用正确的名字导入，`import {User}` 写成 `{MyUser}` 直接失败；
- 默认导出导入时**名字随便起**（`import User` / `import MyUser` 都有效）→ 团队成员可能用不同名字导入同一个东西，不好；
- 常见约定：导入变量名与文件名对应，如 `import User from './user.js'`、`import LoginForm from './loginForm.js'`；
- 一些团队视其为严重缺陷，**始终只用命名导出**（哪怕只导出一个东西）——这也让重新导出更容易（见下节）。

### 6. 重新导出：`export ... from ...`

```js
export {sayHi} from './say.js';            // 重新导出 sayHi
export {default as User} from './user.js'; // 重新导出默认导出
```

**典型场景：包（package）的单入口模式。** 一个包含大量模块的文件夹，只通过"主文件"对外暴露功能，内部 helpers 不对外可见：

```
auth/
    index.js   ← 唯一对外入口
    user.js
    helpers.js
    providers/
        github.js
        ...
```

外部只从主文件导入：`import {login, logout} from 'auth/index.js'`。主文件的两种写法等价：

```js
// 写法一：先导入再导出
import {login, logout} from './helpers.js';
export {login, logout};
import User from './user.js';
export {User};

// 写法二：export ... from 简写（一行搞定）
export {login, logout} from './helpers.js';
export {default as User} from './user.js';
```

**重要区别：`export ... from` 重新导出的东西在当前文件中不可用**——上面的 `auth/index.js` 里不能直接使用 `login/logout`（简写没有把名字绑定进当前模块作用域）。

#### 重新导出默认导出的两个坑

假设 `user.js` 里是 `export default class User`：

1. **`export User from './user.js'` 是无效语法！** 重新导出默认导出必须显式写 `export {default as User} from './user.js'`；
2. **`export * from './user.js'` 只重新导出命名导出，会忽略默认导出。** 想两者都重新导出需要两条语句：

```js
export * from './user.js';        // 命名导出
export {default} from './user.js'; // 默认导出
```

默认导出在重导出时的这种别扭，正是部分开发者讨厌它的原因之一。

### 7. 全部语法形式汇总

导出：

```js
// 声明前
export [default] class/function/variable ...
// 独立的导出
export {x [as y], ...}
// 重新导出
export {x [as y], ...} from "module"
export * from "module"                // 不重新导出默认导出
export {default [as y]} from "module" // 重新导出默认导出
```

导入：

```js
import {x [as y], ...} from "module"  // 命名导出
import x from "module"                // 默认导出
import {default as x} from "module"   // 默认导出的另一种写法
import * as obj from "module"         // 全部导入为对象
import "module"                       // 只加载并运行模块代码，不绑定任何导出
```

### 8. `import`/`export` 的位置

- 放在脚本顶部或底部**都可以**（声明会被提升），下面这样技术上没问题：

```js
sayHi();
import {sayHi} from './say.js'; // 在文件底部导入
```

实践中导入通常放文件开头，纯粹为了方便。

- **但 `{...}` 块中的 import/export 无效**，有条件的导入是不行的：

```js
if (something) {
  import {sayHi} from "./say.js"; // Error: import must be at top level
}
```

真有"按条件/按需加载"的需求 → 用下一篇的**动态导入**。

## 与 Java 对比

| Java | JS | 说明 |
|---|---|---|
| `import com.foo.User;` 一种形态 | 命名导入 / 默认导入 / `import * as` / 副作用导入 四种形态 | JS 导入语法远比 Java 丰富 |
| `import static` 无法改名 | `import {x as y}` | JS 的 as 类似 SQL 别名 |
| 无对应 | `export default`（一文件一实体） | 类似"一个 Java 文件只放一个 public 类"的惯例，但被语法化且引发争议 |
| `import com.foo.*` | `import * as obj` | JS 拿到的是**一个对象**，且不利于 tree-shaking |
| 无对应（package 不能聚合重导出） | `export ... from` 重新导出 | 实现门面（Facade）模式的语言级支持 |
| — | 块级 `import` 非法，必须顶层 | Java 的 import 本来就在编译单元顶层，约束一致 |

## 一句话总结

导出三分法：声明前 `export`、尾部 `export {...}`、`export default`；导入四分法：`import {x}`（命名）、`import x`（默认，无花括号）、`import * as obj`、`import "mod"`（纯副作用）；`as` 两边都能改名；默认导出可匿名但每文件一个，重新导出时它必须单独用 `export {default ...} from` 处理且 `export *` 会漏掉它；`export ... from` 是包单入口的利器但导出的名字当前文件用不了；import/export 只能写在顶层，有条件加载交给动态导入。
