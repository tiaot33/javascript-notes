# 01 模块（Module）简介

> 原文：`zh.javascript.info/1-js/13-modules/01-modules-intro/article.md`
> JS 的模块 = 一个文件，粒度比 Java 的 package 细得多，更接近"一个 Java 文件就是一个类"的世界。模块间靠 `export`/`import` 显式交换功能，类似 JPMS 的 `exports`/`requires`，但加载语义是 JS 特有的。

## 知识点

### 1. 历史背景

JS 长期没有语言级模块语法，社区造过几套方案（都已慢慢成为历史，旧代码里还能见到）：

- **AMD** —— 最古老的模块系统之一，require.js 实现；
- **CommonJS** —— 为 Node.js 服务器创建的模块系统；
- **UMD** —— 通用方案，同时兼容 AMD 和 CommonJS。

ES6（2015）把模块做进了语言标准，现在主流浏览器和 Node.js 都支持。

### 2. 什么是模块

- **一个模块就是一个文件。一个脚本就是一个模块。**
- 两个指令交换功能：
  - `export` 标记可从模块外部访问的变量/函数；
  - `import` 从其他模块导入功能。

```js
// 📁 sayHi.js
export function sayHi(user) {
  alert(`Hello, ${user}!`);
}

// 📁 main.js
import { sayHi } from './sayHi.js'; // 相对当前文件的路径
sayHi('John'); // Hello, John!
```

- 浏览器需要用 `<script type="module">` 明确告诉浏览器按模块处理（模块有特殊关键字和功能）。浏览器会自动获取并解析导入的模块（包括导入的导入），然后运行。
- **模块只通过 HTTP(s) 工作**：用 `file://` 本地打开网页，`import/export` 不起作用。本地测试用 static-server 或 VS Code 的 Live Server。

### 3. 模块核心功能（浏览器和服务端通用）

#### 3.1 始终严格模式

模块始终运行在 `"use strict"` 下，无需手写。例如给未声明变量赋值直接报错。

#### 3.2 模块级作用域

- 每个模块有自己的**顶级作用域**：模块内顶级变量/函数对其他脚本不可见。
- 正确姿势：模块 `export` 想被外部访问的，`import` 需要的——**不依赖全局变量**。
- 浏览器中，同一页面的两个 `<script type="module">` 也互看不到对方的顶级变量：

```html
<script type="module">
  let user = "John"; // 只在这个 script 内可见
</script>
<script type="module">
  alert(user); // Error: user is not defined
</script>
```

- 后门：显式挂到 `window.user = "John"` 可以成为窗口级全局变量，所有脚本可见——但**不是好方式，尽量避免**。

#### 3.3 模块代码只在第一次导入时执行一次

同一个模块被多处导入，代码只执行**一次**（首次导入时），导出结果被后续所有 importer 共享。推论：

- **副作用只触发一次**：

```js
// 📁 alert.js
alert("Module is evaluated!");

// 📁 1.js
import './alert.js'; // 弹窗
// 📁 2.js
import './alert.js'; // 什么都不发生
```

- **规则：顶层模块代码应用于初始化**（创建模块内部数据结构）；需要多次调用的东西应该导出成函数。
- **导出的对象在所有导入间共享**（同一个引用）：

```js
// 📁 admin.js
export let admin = { name: "John" };

// 📁 1.js
import { admin } from './admin.js';
admin.name = "Pete";

// 📁 2.js
import { admin } from './admin.js';
alert(admin.name); // Pete —— 1.js 的修改在 2.js 可见，是同一个对象
```

- 由此得到**配置模块**的经典模式：
  1. 模块导出一个配置对象（如凭证 `config`）；
  2. 应用顶层脚本首次导入时给配置赋值；
  3. 后续导入者拿到的都是已配置好的模块。

```js
// 📁 admin.js
export let config = { };
export function sayHi() {
  alert(`Ready to serve, ${config.user}!`);
}

// 📁 init.js（应用的第一个脚本）
import { config } from './admin.js';
config.user = "Pete";

// 📁 another.js
import { sayHi } from './admin.js';
sayHi(); // Ready to serve, Pete!
```

#### 3.4 `import.meta`

- 包含当前模块的信息，内容取决于环境；浏览器中是脚本的 URL（内联脚本则是所在页面的 URL）：

```html
<script type="module">
  alert(import.meta.url);
</script>
```

#### 3.5 模块中顶级 `this` 是 `undefined`

```html
<script>alert(this)</script>             <!-- window -->
<script type="module">alert(this)</script> <!-- undefined -->
```

### 4. 浏览器特定功能

#### 4.1 模块脚本总是延迟的（≈ `defer`）

对外部脚本和内联脚本都生效：

- 下载不阻塞 HTML 解析，与其他资源并行加载；
- 等 HTML 文档**完全就绪**后才运行（哪怕模块很小加载更快）；
- 保持文档中脚本的相对顺序（排前面的先执行）。

副作用：

- 模块脚本能"看到"已完全加载的页面，包括它**下方**的 HTML 元素（常规脚本看不到，因为它立即执行）；
- 注意执行顺序反直觉：常规脚本先于模块脚本运行；
- 用户可能在 JS 就绪前就看到了页面，某些功能暂不可用——应放置加载指示器。

#### 4.2 `async` 对内联模块脚本也有效

- 常规脚本的 `async` 只对**外部**脚本有效；模块脚本对内联也有效。
- `async` 模块脚本准备好（含其 import 全部 fetch 完）就立即运行，不等 HTML 也不等其他脚本。
- 适合不依赖其他东西的功能：计数器、广告、文档级事件监听器。

```html
<script async type="module">
  import {counter} from './analytics.js';
  counter.count();
</script>
```

#### 4.3 外部脚本的两条规则

1. **相同 `src` 只运行一次**：两个 `<script type="module" src="my.js">` 只加载执行一次；
2. **跨源需要 CORS**：从另一个源获取的模块脚本，远程服务器必须提供 `Access-Control-Allow-Origin` header，否则不执行（默认更好的安全性）。

#### 4.4 不允许裸模块（bare module）

- 浏览器中 `import` 必须给出**相对或绝对 URL 路径**，没有路径的"裸"模块是错误：

```js
import {sayHi} from 'sayHi'; // Error，必须写成 './sayHi.js' 之类的路径
```

- Node.js 和打包工具允许裸模块（它们有自己的查找规则和 hook），浏览器不支持。

#### 4.5 兼容性后备：`nomodule`

旧浏览器不认识 `type="module"` 会直接忽略该脚本；用 `nomodule` 给它们提供后备脚本：

```html
<script type="module">
  alert("Runs in modern browsers");
</script>
<script nomodule>
  alert("现代浏览器跳过这里；旧浏览器忽略 type=module，执行这里。");
</script>
```

### 5. 构建工具

实际开发很少"裸用"浏览器模块，通常用 Webpack 等工具打包后部署：

1. 从 HTML 中的"主"模块 `<script type="module">` 开始；
2. 分析依赖（导入的导入……）；
3. 把所有模块打包成一个（或多个）文件，用打包函数（bundler function）替代原生 `import`；还能支持裸模块、CSS/HTML 模块等特殊类型；
4. 打包过程中可做各种转换优化：
   - 删除不可达代码；
   - **tree-shaking**：删除未使用的导出；
   - 删除 `console`、`debugger` 等开发期语句；
   - 用 Babel 把现代语法转译成旧语法；
   - 压缩（去空格、短变量名）。

打包产物里不再有任何 `import/export`，因此也**不需要 `type="module"`**，普通 `<script src="bundle.js">` 即可。

### 6. 总结

1. 一个模块就是一个文件；浏览器需要 `<script type="module">`；模块脚本相对常规脚本的差异：默认延迟、async 可用于内联、跨源需 CORS、重复 src 只跑一次；
2. 模块有自己的顶级作用域，通过 `import/export` 交换功能；
3. 模块始终严格模式；
4. 模块代码只执行一次，导出只创建一次并在所有导入间共享。

## 与 Java 对比

| Java | JS | 说明 |
|---|---|---|
| package（目录级）+ JPMS `module-info` | **一个文件就是一个模块** | 粒度天差地别 |
| `public` / JPMS `exports` | `export` 关键字 | 显式声明可访问面 |
| `import`（编译期符号解析） | `import './x.js'`（带路径，运行时真的会加载执行文件） | JS 的 import 有加载语义 |
| 类加载器保证类只初始化一次 | 模块代码只在首次导入时执行一次 | 导出对象天然是**单例** |
| Spring 的 `@Configuration` + 注入 | 导出 `config` 对象，顶层脚本首次导入时赋值 | "配置模块"经典模式 |
| — | 模块级作用域，顶级变量不污染全局 | Java 靠类封装，JS 模块文件自带隔离 |
| — | `type="module"` 的加载语义（defer/CORS/裸模块限制） | 纯浏览器侧概念，Java 无对应 |
| Maven/Gradle 打包 + ProGuard 压缩 | Webpack 打包 + tree-shaking + Babel | 角色类似 |

## 一句话总结

模块 = 文件，浏览器用 `<script type="module">` 启用（且必须走 HTTP(s)）；模块天生严格模式 + 独立顶级作用域，代码只在首次导入时执行一次、导出被所有导入者共享（可做配置单例）；浏览器侧还要记住：模块永远延迟执行、async 可用于内联、跨源要 CORS、`src` 去重、不支持裸模块、`nomodule` 做旧浏览器后备；生产环境交给 Webpack 打包（tree-shaking、Babel、压缩）。
