# 02 Eval：执行代码字符串

> 原文：`zh.javascript.info/1-js/99-js-misc/02-eval/article.md`
> "eval is evil"——了解它是什么、为什么现代代码几乎不再用它，以及两个标准替代方案。

## 知识点

### 1. 基本用法
```js
let result = eval(code); // 执行代码字符串，返回最后一条语句的结果
eval('1+1');              // 2
eval('let i = 0; ++i');  // 1
```

### 2. 在当前词法环境中执行（危险来源）
```js
let a = 1;
function f() {
  let a = 2;
  eval('alert(a)'); // 2 —— 读到的是最近的局部变量
}
eval("x = 10"); // 甚至能修改外部变量
```

### 3. 严格模式 vs 非严格模式
- **严格模式**：`eval` 有自己的词法环境，内部声明的 `let`/函数**不外泄**：
```js
eval("let x = 5; function f() {}");
typeof x; // undefined（外部访问不到）
```
- 非严格模式：`eval` 没有自己的词法环境，`x` 和 `f` 会污染外部作用域。

### 4. 为什么"eval 是魔鬼"
1. **阻碍压缩**：压缩工具（minifier）会把局部变量重命名为 `a`/`b`，但 `eval` 里的代码可能按名字访问这些变量，工具不敢重命名 → 压缩率下降。
2. **可维护性差**：字符串里的代码读写外部局部变量，是隐式副作用，重构时极易踩雷。
3. **历史原因已消失**：十年前 JS 能力弱，很多事（如解析 JSON）只能靠 eval；现在有 `JSON.parse`、模块、动态 `import()` 等现代结构，几乎找不到用它的理由。

### 5. 两个替代方案（避免副作用）
- **代码不需要外部变量** → 用 `window.eval(code)`，让它在**全局作用域**执行：
```js
let x = 1;
{
  let x = 5;
  window.eval('alert(x)'); // 1（拿的是全局变量）
}
```
- **代码需要外部数据** → 用 `new Function`，显式传参：
```js
let f = new Function('a', 'alert(a)');
f(5); // 5
```
`new Function` 也在全局作用域创建（访问不到局部变量），把数据作为参数传入，依赖关系一目了然。

## 与 Java 对比
| Java | JS | 说明 |
|---|---|---|
| 无内建等价物；近似：GroovyShell、JShell、运行时编译（JavaCompiler API）、SpEL 表达式引擎 | `eval(code)` | JS 解释器随手可执行代码字符串，Java 需借助脚本引擎/编译器 |
| 表达式求值推荐 SpEL / MVEL | 推荐 `new Function` 显式传参 | 两者都把"数据"与"代码"分离 |
| 反射修改局部变量（做不到） | eval 能读写外层局部变量 | JS 词法环境动态性远超 Java，这也是它危险的原因 |

## 一句话总结
`eval(code)` 执行代码字符串并返回最后一条语句的结果，且在**当前词法环境**中运行（能读甚至改外部变量，严格模式下声明不外泄）；它破坏压缩、隐藏依赖、可维护性差，现代 JS 基本不用——不需要局部变量就用 `window.eval` 去全局执行，需要数据就用 `new Function('a', body)` 显式传参。
